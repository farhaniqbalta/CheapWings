## 1. Architecture review — P4.9 admission as merged

One worker process runs one asyncio loop (`JobRunner.run`: `tick` → `pause`).
`tick` round-robins over registrations from a persisted cursor. For each
provider it applies, in order: a capacity check, the start-interval check, then
an atomic SQLite claim (`Repository.claim`, `BEGIN IMMEDIATE`). A claimed item
becomes an asyncio task. The adapter call is shielded, so a logical timeout
records the failure while the physical call keeps its slot until it really ends.

The per-provider ceiling was enforced twice and configured in three places:

| Kind | Location (P4.9) | P4.12 |
|---|---|---|
| Scheduler ceiling | `job_runner.py` `tick`: `min(reg.concurrency, blocking.capacity)` vs `occupied(pid)` | Removed; only an adapter's real thread pool can refuse (see below) |
| Scheduler ceiling (DB) | `repository.py` `claim`: per-provider running count vs `registration.concurrency` | Removed; the global running count (shared op counted once) stays |
| Configuration | `Registration.concurrency`; `Settings.<pid>_concurrency` (1..16); `<PID>_CONCURRENCY` env | Removed |
| Adapter-intrinsic limit | `BoundedCall` thread pool (swoop, Fli) — no queueing, slot held until the thread exits | Kept, documented as adapter limit: Fli pool = G (threads spawn lazily); swoop fixed 3 (obsolete, not optimized) |
| Start-rate control | In-memory `_next_start` at actual adapter entry; persisted `ProviderState.next_request_at` reserved at claim; one pending start per paced provider | Unchanged |
| Protocol gate | OctoTrip `HttpStartGate` ≥1.10s across MCP sessions; Fli internal 429 backoff | Unchanged |
| Global safety limit | `occupied()` = Σ max(logical tasks, busy threads); `WORKER_MAX_IN_FLIGHT` 1..64 | Unchanged logic; range 1..100, default stays 9 |

Fairness reused as is. Across providers, the cursor dispatches one item per
provider per pass and resumes after the last one served, so a released slot goes
to the next provider with eligible work. Across jobs, the persisted
`SearchJob.dispatch_sequence` serves the least recently served job first and
survives restarts. With caps removed, a provider fills G only while no other
provider has eligible work. Paced providers stay naturally bounded at about
latency ÷ interval.

**Limitation (documented, not mitigated):** admission is fair, but running
operations cannot be preempted. A slow provider that fills the pool while it is
the only one with work keeps those slots until its calls finish. New work for
another provider then waits for the first release (§5, scenarios 4 and 7).

## 2. Implementation

- `application/job_runner.py`: the provider ceiling is gone. A blocking adapter
  is skipped only when `occupied(pid) >= blocking.capacity`. `occupied()` counts
  dispatched tasks that have not yet entered the thread pool, which closes a
  dispatch-overrun gap the old implicit C1 default had masked.
- `storage/repository.py`: the per-provider count is removed from `claim()`.
- `providers/registry.py`: `Registration.concurrency` is removed. Fli's
  `BoundedCall` is sized to `WORKER_MAX_IN_FLIGHT`; swoop keeps 3.
- `config.py`: `<pid>_concurrency` is removed and `WORKER_MAX_IN_FLIGHT` is
  allowed 1..100.
- No schema change, migration, new service or new dependency.

- **P4.12:** blocking pool = G.
- **Run limits:** each variant was capped at 15 minutes per the owner, with

  P4.12 completed 178 (4–5).
- **Artifacts:** raw `scripts/benchmarks/artifacts/p412_p49.jsonl` and

  `p412_report.py`.

Successful operations per minute at G9: one provider 530 → 1468; fast + slow
406 → 1019; large/small 1059 → 1590. P4.9 throughput does not change between G9
and G64 in any scenario: its peak in-flight is 3 × (providers with work), and
useful slot use falls from 31–62% at G9 to 4–9% at G64.

Time to first valid result (earliest job): unchanged or better in most cells
(−1% to −29%), because P4.9 already started the first calls immediately. The
worst-served small job in scenario 9 improved from 0.63s to 0.36–0.40s at G16+.

**Cases where P4.12 is slower:**
- **Late job behind a pool-filling slow provider** (scenarios 4 and 7 at
  G9/G16). The new job's first result goes from 0.13s to 1.08s (scenario 4, G9)
  and from 0.20s to 0.43s (scenario 7, G9/G16): it waits for one slow operation
  to finish. This disappears at G32+, where the slow provider ran out of work
  before filling the pool. Total completion still improved 42–59%.
- **Pacing-bound mix** (scenario 3): within ±2% (noise). Start intervals, not
  slots, limit throughput, so removing the cap gives nothing.
- **Graceful restart** (scenario 8): completion equal, ±6%, because it is
  dominated by the 13s claim lease. More in-flight work is interrupted at
  shutdown, so retries rise from 2 to 8 at G9 and from 5 to 32 at G64. That
  means more repeated upstream requests after a restart. Fencing held: no late
  overwrite and no duplicate commit.
- **G100 stress, first result:** 0.37s → 0.59s, under event-loop saturation
  (below).

Resource use: CPU per scenario fell 10–64% in the slot-bound scenarios, because
each finished operation costs the same and the run spends less time idle-polling.
It rose in the restart scenario (+32% at G9, from the re-executed work) and was
within ±6% in the pacing-bound scenario. Peak RSS was about
113–121 MB across the whole P4.12 run, and memory did not grow with G.
`ru_maxrss` is process-wide, so per-trial RSS was not isolated.

**G100 bottleneck (profiled, cProfile, one trial).** P4.12 reached 100 in flight
but only 25% useful utilization; the ideal is about 3.2s against 42.9s measured.
CPU time roughly equals wall time, so the single event loop is saturated. 41s of
52s is `Repository.finish`:
- `finalize()` reloads every work item of the job on each finish. That is 2.9M
  ORM rows for 1,600 finishes, O(job size²).
- `_store_results` builds a new pydantic `TypeAdapter` schema on every call:
  4,000 constructions, about 8s.

Both are pre-existing P4.9 costs. They scale with job size, not G or provider
concurrency. The stress job (1,600 items) exceeds the production per-search
ceiling (120 combinations × 4 providers = 480). Not changed in P4.12: these are
persistence optimizations outside this milestone's scope, and they are the
first thing to fix if G or job size grows.

Limits: synthetic adapters on one Mac with 2–5 repeats. The results model
scheduler behaviour and are not a live speed forecast. Live providers are
dominated by their own latency, start intervals and throttling.

## 6. Risk analysis

- **Pool monopolization (main live risk).** With local OctoTrip at 1s and about
  25–42s live latency, OctoTrip alone can hold about 25–40 operations. At G9 it
  could occupy the whole pool for one latency period whenever it is the only
  provider with eligible work. A search for other sources started in that window
  waits up to one OctoTrip latency for its first result; scenario 4 shows the
  same effect at synthetic scale. Admission stays fair as soon as slots release.
  Possible mitigations need an owner decision because each reintroduces a form
  of partition the brief rejected:
  1. Raise G so paced providers cannot fill it (OctoTrip at 5s fills about 5–9).
  2. Keep a small free-slot headroom for providers with no running work.
  3. Accept it.
- **Slow or stuck transports** hold slots until the I/O really ends. This is
  unchanged by design, and a stuck blocking thread still needs process
  termination. With the cap removed, more slots can be held at once.
- **Provider overload.** No provider can start faster than before, because start
  intervals, the OctoTrip HTTP gate, Retry-After and cooldowns all still apply.
  In-flight count per provider is now about latency ÷ interval instead of ≤3,
  which is a heavier concurrent load on slow providers (OctoTrip, Skiplagged).
  No adaptive overload safeguard was added (owner decision); 429 cooldowns,
  retry budgets and pacing remain the protection.
- **Fli threads** can reach G (9 by default). At 1s pacing and about 2–5s
  latency that is about 2–5 threads in practice.
- **Restart cost:** more in-flight work means more re-executed upstream calls
  after an interrupted worker.

## 7. Recommended production configuration

Evidence supports removing the cap: every slot-bound scenario improved 30–86% in
completion time at the same G, and nothing regressed on correctness. Evidence
does **not** yet support a specific production G. All results are synthetic, and
the one regression (late job behind a pool-filling slow provider) is sensitive
to live OctoTrip latency and interval. Recommendation: keep `G=9` and current
intervals. If the owner wants more parallelism, try G16 locally with OctoTrip at
its 5s default before any live validation. No live run was made; any live
validation needs separate owner approval.

## Follow-up — priority tiers and low-priority headroom (2026-11-12)

Owner decision on §8.1: OctoTrip gets the lowest priority, plus headroom. Priority
alone was not enough. Running calls cannot be preempted, so a low-priority
provider that was the only one with work could still fill every slot.

- `Registration.priority` (0 = highest), configured per provider by
  `<PROVIDER>_PRIORITY`, range 0..9. Defaults: Skiplagged, swoop and Fli 0;
  OctoTrip 1.
- `tick()` orders providers by tier and round-robins inside a tier using the
  existing cursor. The sort is stable, so the rotation is preserved. A lower
  tier is reached only when no higher tier can dispatch: no eligible work,
  pacing, cooldown or thread pool full.
- `LOW_PRIORITY_HEADROOM` (default 2, range 0..G−1): a provider below the best
  *available* tier may not take the last N slots. With G9, OctoTrip runs at most
  7 calls while any higher-tier source is enabled. With no higher-tier source
  available, it can use all G slots.
- Accepted trade-offs:
  - OctoTrip waits whenever higher tiers have eligible, unpaced work.
  - Up to N slots can sit idle while only OctoTrip has work.
  - This is a dynamic reservation for higher tiers, not a fixed per-provider
    ceiling.
- Tests, added to `test_p412_pool.py`:
  - Strict tier order holds regardless of registry order.
  - A late higher-tier job starts on the next tick instead of waiting for a
    0.5s low-tier call.
  - Headroom is unused when no higher tier exists.
  - Configuration defaults, environment override and the bound check.
