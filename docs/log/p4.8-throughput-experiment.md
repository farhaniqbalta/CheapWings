## Authorization and method

The owner authorized live concurrency 1→2 and conditional concurrency 3, offline stress/failure injection, a separate result log, and later removed the assistant's proposed fixed live-traffic cap. No production implementation, deployment, automatic merge or push is authorized by this experiment. Experiments use finite comparison batches; there is no automatic open-ended load generator.

Read current WORK_LOG, registry, JobRunner, Repository/SQLite transactions, cache/operation coalescing, worker ownership, and all three adapters. On notice of new work-log rules, reloaded WORK_LOG and preserved the owner's concurrent README/docs restructuring. Results belong here, with a short pointer in the main log.

- Actual production adapters and production JobRunner/Repository execute in disposable migrated SQLite databases. Production default concurrency remains 1 and interval 15s. Benchmarked registration overrides and adapter pooling are isolated in `scripts/benchmarks/p48_throughput.py`; no backend source or installed dependency changed.
- Eight distinct route/date searches per live configuration; application cache/coalescing/repricing off, zero retries, unchanged request normalization. All sources run independently; each source's configurations run sequentially. The same eight searches repeat across a comparison, with deterministic shuffled admission order and bracketing concurrency-1 controls when possible. Each call still makes its actual upstream POST(s).
- Initial corpus: MEL→DPS/SIN and CGK→DPS/SIN on 2027-01-19/20 (eight units), USD, economy, one adult. The swoop January corpus returned eight valid empty responses per batch; those timings are not evidence of offer-bearing search throughput. Its follow-up matched corpus is MEL→DPS on 2026-12-15…22, which returned priced offers.
- Provider response caches cannot be disabled/dated through the supported adapter interfaces. Application cache is disabled, source payloads are not changed to evade caching, and no freshness is invented. Bracketing runs/randomized order reduce but cannot eliminate server-cache and temporal confounding. Skiplagged's 429 prevented its post-treatment baseline; its apparent speedup cannot be assigned wholly to concurrency.
- Any 429/401/403 blocks further HTTP starts to that source immediately; drain already-started operations without retrying, discard unsent work and skip all later configurations. Other adapter failures also stop that source's trial conservatively. Stop state is checked at HTTP-send boundaries as well as scheduler admission. A previously stopped source is not retried to bypass rejection. OctoTrip's first timeout-only trial was later repeated after a long rest/host-stability check, with a less aggressive logical interval; it had no 429/block response.
- At concurrency >1, use a bounded pool of unchanged production adapter instances, preserving each swoop instance's one-thread BoundedCall. A timed-out thread's instance is quarantined, never returned as a free slot. This tests an explicit experimental architecture, not a stock single-adapter scheduler configuration. Offline tests separately prove that stock swoop rejects its second overlapping invocation.
- OctoTrip uses one **shared ≥1.10s HTTP-start gate across all concurrent sessions**, including initialize and tools/call. No intentional burst usage, retries, alternative proxy/session identity, challenge solving or protective-measure workaround. Only one OctoTrip benchmark process sends traffic at a time.
- Telemetry contains timestamps, route/date, counts, status/error codes and Retry-After only. Raw payloads, selectors, booking URLs and credentials are never written into result artifacts. Temporary databases hold normalized results only during a run and are removed afterward.

## Metric definitions and host validity

Batch time includes job admission and durable queue draining. Searches/minute counts **committed successful work items**, including explicitly successful empty responses; priced offer counts are shown separately. Time to first result is the first normalized successful adapter return, just before its synchronous SQLite result commit; it is not browser render latency. Latency includes pool admission, protocol setup, actual response/stream parsing and normalization. p50/p95 use nearest-rank quantiles; **with eight observations p95 is the maximum**, not a stable tail estimate. Partial/failed batches are excluded from reliable-configuration rankings.

Maximum logical in-flight count and actual search-HTTP overlap are separate. HTTP overlap is measured from each tools/call (or swoop POST) send boundary until that adapter returns/aborts; its end conservatively includes final parsing/protocol cleanup. Claimed concurrency without measured HTTP overlap does not qualify as parallel provider search. Actual inter-start gaps are recorded, not inferred from settings.

One initial host sleep/wall-vs-monotonic discontinuity of about **148.75s** caused expired durable leases even though awake-time adapter latency looked normal. Affected synthetic 30s/C1, synthetic 15s/C2 and the first OctoTrip C1 baseline are retained as diagnostic evidence, excluded from rankings, and repeated with `/usr/bin/caffeinate -i`. Later runs record both wall and monotonic batch time and reject material clock divergence. The inhibitor prevents idle sleep, not manual system sleep. This is also evidence that wall-clock lease fencing matters during host suspension.

Offline resource measurements are per separate benchmark process, not per provider in the combined live process. CPU is process CPU time/wall time as a percentage of one core. macOS ru_maxrss is the process lifetime RSS high-water mark, not an incremental per-batch allocation. Allocation-traced diagnostic runs are separated from fresh-database, tracing-disabled fast throughput comparisons. Trials on different latencies use separate databases/processes; concurrent host activity is a limitation. No external requests are made by synthetic or failure-injection tests.

### What was reliable, what was fast

- **Skiplagged:** C1/1s took 50.518s for 8/8 and 160 accepted offers; C2/1s took 14.318s, 8/8, 160 offers, with real independent adapter invocations in flight. The 3.53× raw speed ratio is **not a causal concurrency-only gain**: median service latency fell from 5.914s to 2.935s, and the required post-treatment baseline could not run after the subsequent rejection. C2/0.25s hit **HTTP 429, Retry-After 60**, completed 6/8 and was stopped permanently for this experiment. A peer already in progress also ended in ExceptionGroup after its unsent follow-up was blocked. Only one HTTP 429 occurred. The MCP ExceptionGroup obscured `http_rate_limited` from the production adapter/runner, confirming the classification gap. No C3 test and no post-block retry were attempted. Higher RPS, accumulated quota, caching and temporal effects cannot be separated from this run.
- **swoop:** C2/0.25s and C2/0.5s initially yielded a search-span peak of **1**, so they do not count as demonstrated parallel HTTP search. The stock-instance offline experiment also accepted only one actual invocation. With a bounded two-instance pool and a matched offer-bearing corpus, C2/0.1s produced peak **2**, 8/8 successes, 80 offers in **1.307s (367.21/min)**. Bracketing C1/0.1s batches took **3.375s and 2.292s**, each 8/8 with 80 offers. A repeat control before considering C3 then failed after **4 attempted / 3 successful** calls, with HTTP 200 plus `provider_unavailable` (29 accepted offers). The underlying source-error cause is unresolved; do not label it a proven rate limit or ignore it as an empty result. Stopped immediately and skipped C3. Therefore C2/0.1s is a peak-speed observation, **not a repeatably reliable recommendation**.
- **OctoTrip:** the initial C1/1s baseline was host-sleep-contaminated; the following C2/1s attempt timed out twice at 90s and stopped at 2/8 attempted. No 429/block was observed. A later, clean controlled comparison gave C1/3s **168.641s before and 245.781s after**; C2/3s **155.204s**; C2/5s **132.102s**; all 8/8 with 41 accepted offers. C2/3s was more than 20% faster than the mean bracketing baseline, the predeclared warrant for C3. Conditional C3/3s achieved peak **3**, 8/8 and 41 offers, but took **189.066s**, with p50/p95 **59.047/82.763s**. The winning clean batch was **C2/5s, 3.63 successful searches/minute**; C3/3s gave only 2.54/min. Increasing concurrency and reducing the interval did not produce the fastest result. No throttling is inferred merely from slower responses. Time/response variability and source-side contention are plausible confounders, not demonstrated causes.

Across all OctoTrip benchmark processes, the smallest observed send-boundary HTTP-start gap was **1.1002s**. The gate covered every initialization and tools/call across concurrent sessions. Application search intervals were not substituted for the published HTTP quota. The initial and later OctoTrip processes did not run simultaneously.

Completion/deadline-driven wakeups should be evaluated before increasing polling frequency in production.

The original allocation-traced fast matrix reused growing historical databases; it reached 64/C32 in 2.761s. The final fresh, untraced matrix reached **1.043s**, about **3683/min**, with **56.9%** of one core and **82.8MiB** RSS high-water. The final dispatch metric uses queue readiness/available capacity; for zero interval it does not incorrectly treat the preceding actual start as the readiness anchor.

**Finding:** Python asyncio did not impose the live throughput ceiling in these tests. At 5–30s latencies the worker scaled close to C-way service overlap; at 0.25s and high concurrency, synchronous ORM/SQLite work, result commits and tick polling create measurable dispatch/loop delays. The 32-call test's p95 loop lag is about 141ms, so this is not a claim of unlimited capacity or hard real-time responsiveness. The full stress workload is much faster than the observed live providers. With provider concurrency ≤3 and multi-second network waits, replacing the language is not supported by the measurements.

## Implementation plan addressing speed and correctness

Implementation remains **unapproved and unstarted**. Preserve the existing separate durable Python worker, SQLite BEGIN IMMEDIATE claims, lease tokens, coalesced ProviderOperations, cache eligibility/expiry, repricing budgets and cancellation/result fencing.

1. **Fix provider feedback independently of work-result commit.** Introduce a short durable provider-feedback transaction that raises next_request_at using max(current, received_at + required delay), even when cancellation, lease expiry or job deadline fences the result. It must not renew a lease, authorize an otherwise invalid retry, or write quotes. Normal/direct/shared completion may apply the same max idempotently. Turn the cancellation/429 expected failure into a pass before any faster rollout.
2. **Preserve rate-limit classification and Retry-After.** Recursively handle nested MCP ExceptionGroup HTTP status exceptions without persisting raw exception text; the observed Skiplagged 429/60s must become http_rate_limited with at least 60s global cooldown. Parse integer and HTTP-date Retry-After. The pinned swoop SDK discards raw headers; review a minimal pinned SDK/upstream patch to expose them rather than replacing the transport or silently upgrading. Its observed HTTP-200 provider_unavailable stays an unresolved failure, not an invented 429 or empty success. Maintain zero hidden SDK retries and bounded application retries.
3. **Configure interval and capacity separately per provider.** Add finite positive real-provider interval settings and bounded integer concurrency settings, defaulting to existing 15s/C1 until approval. Validate that actual adapter capacity matches the requested concurrency. A single swoop adapter has capacity 1; C2 requires an explicit bounded instance/slot pool. Claimed capacity must include running direct work, shared operations and actual unfinished blocking futures across jobs.
4. **Keep the limiter independent of capacity.** Durable logical start pacing remains provider-wide; freeing a slot never bypasses next_request_at, cooldown or retry eligibility. No mandatory interval after completion, no catch-up burst, no global sleep blocking other providers. Cache hits consume no provider capacity; identical in-flight queries retain the existing single shared operation. Do not add execution settings to fare/cache identity or bypass coalescing for production throughput.
5. **Enforce OctoTrip HTTP quota across every slot.** Use one shared monotonic start gate covering all initialize/tools-call messages, including waiting and cancellation. Do not install one limiter per adapter instance or per job. Persist provider cooldown through SQLite; apply it to all slots. A future multi-process transport requires one owner/broker for this gate, not independent process-local quotas.
6. **Retain physical slots through timeouts/cancellation.** Return a pool slot only when its actual underlying future/transport is finished. Quarantine stuck slots; do not queue unbounded executor work or consume retry attempts merely because a previous cancelled thread still owns the slot. Claim only when real capacity exists. Use process isolation only if measured real stalls warrant killable SDK workers; a client process kill does not guarantee the remote read stopped.
7. **Handle host suspension explicitly.** Retain persisted wall-clock leases and fencing. Detect large wall/monotonic divergence for observability and recovery; expired work cannot accept late results. Do not hide suspension by extending old leases/retention or by claiming a call's awake-time latency implies its wall-clock lease remains valid.
8. **Optimize wakeups/maintenance only after profiling.** Evaluate a completion event plus earliest provider/retry deadline and bounded periodic lease/purge maintenance, preserving cancellation responsiveness and crash recovery. The 10ms poll test improved fast synthetic batch time but doubled CPU use; do not simply busy-poll faster. At C32, investigate synchronous ORM/result-commit bursts before introducing another runtime.
9. **Approve and validate configuration rollout separately.** Revalidate Skiplagged only after cooldown/block investigation and explicit authorization; never use another transport/session/IP to evade rejection. Revalidate swoop's failed parallel pair before recommending it. For OctoTrip, C2/5s is the measured speed candidate; higher C3 was slower. Run focused fault regressions and the full backend suite before a controlled restart. Rollback preserves a longer persisted provider cooldown and all completed results.

Acceptance gates: all actual-adapter capacities bounded; precise interval/HTTP quota tests across slots; independent providers; short/long calls; Retry-After integer/date/nested-error cases; late-feedback cancellation; shared-subscriber cancellation; stalled threads; actual process recovery; competing claims; no duplicate committed results; immutable cache age and correct retention. No expected failure may remain on the cooldown release gate. No production config, dependency patch or worker restart was performed here.

## Alternative architecture assessment

The estimates below are engineering assessments, **not measured benchmarks of unimplemented systems**. No Rust implementation, new service or new dependency was installed.
