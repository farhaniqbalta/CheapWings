### Current scheduler assessment and review findings

1. `providers/registry.py` already has provider-specific Registration.minimum_interval_seconds/concurrency/timeout fields, but default_registry hard-codes **15s and concurrency 1** for all three. Settings exposes no provider-specific interval environment options.
2. `Repository.claim` uses BEGIN IMMEDIATE, persisted ProviderState.next_request_at and combined running direct WorkItem + ProviderOperation counts. It reserves now + interval **at claim**, never completion + interval. Direct work, coalesced operations and reprice claims share provider state. Finish normally leaves this reservation unchanged. Thus short calls wait only the remainder; calls longer than the interval can dispatch after completion. No additional semaphore, timer wheel or queue system is needed.
3. JobRunner creates independent tasks for each eligible provider on each tick; its 100ms polling loop never waits for one provider's completion before considering another. Worker-local task slots remain occupied for cancelled but unfinished coroutines, in addition to durable running counts. swoop's one-thread BoundedCall shields actual blocking work from cancellation; a still-running thread rejects new submissions rather than accumulating an executor queue.
4. SQLite leases/tokens fence results; sweep only reclaims expired leases. Worker flock permits one queue owner per database. Completed work is not reclaimed. These prevent duplicate claims/commits; an upstream read interrupted between network completion and durable commit can still be repeated by an authorized retry. There is no exactly-once upstream-search guarantee across crashes.
5. Retryable timeout/unavailable/rate-limit failures get bounded attempts and exponential delays (1/2/... seconds capped at 60), with reported Retry-After as a lower bound. HTTP-rate-limit feedback raises the shared persisted next_request_at using max, covering other jobs/searches/reprices and restart. OctoTrip gets a 90s call timeout and ≥100s lease; others use normal 30s/40s defaults. Ordinary slow successes do not trigger cooldowns.
6. Cache admission joins/creates ProviderOperations atomically only when feature/policy permits. Cache hits do not claim provider slots; shared subscribers do not become separate network attempts. Force-refresh freshness rules remain deliberate. OctoTrip can_cache stays false. Cancellation isolates shared subscribers; no P4.8 path may bypass these existing operations or invoke an adapter directly from an API request.
7. **Pacing precision:** current timestamp anchor is durable claim, near logical dispatch, not the actual HTTP tool POST. Protocol setup and thread startup vary. Measured Skiplagged 10s-tier tool-POST gaps were **10.003s and 9.662s** despite logical entry gaps ≥10.095s; resumed swoop 10s tier had a **9.823s** HTTP gap versus a 10.008s logical gap. This is not throttling. Describe the existing guarantee as provider-operation pacing; do not claim strict HTTP spacing. OctoTrip's published per-message rule needs its own transport gate across calls, not just the existing post-initialize sleep.
8. **Confirmed cooldown loss after direct cancellation:** Repository.cancel invalidates a direct lease, then Repository.finish returns False before recording a late 429. The shared operation path retains its operation lease and preserves that cooldown. Isolated strict expected-failure test reproduces the direct defect. Result fencing must remain; provider feedback needs an independent durable update before discarding the cancelled result. This is a release gate, not implemented here.
9. **Retry-After fidelity gaps:** Skiplagged accepts digits only; OctoTrip falls back to 60s for noninteger values, including HTTP dates. Pinned swoop 0.7.0 SwoopRateLimitError discards response headers and the adapter substitutes 120s. No live 429 occurred, so the benchmark respected policy by stopping without testing recovery. Do not claim these production paths fully honor arbitrary Retry-After. MCP nested error classification also needs synthetic coverage before rollout.

### Phase 2 architecture — proposed only

Retain the durable worker and current independent per-provider claim loop. The scheduling unit is one logical provider operation (search or reprice), including its protocol setup; upstream HTTP-message quota enforcement remains inside each transport. Do not introduce a global await/sleep around the registry loop, a per-job provider limiter, or completion-based cooldowns.

A provider is eligible when its durable pacing/cooldown deadline and the work's retry deadline have passed, a valid uncancelled subscriber/job remains within budget/retention, and both durable and local in-flight counts are below **1**. Claim and reserve its next logical start atomically; perform network I/O outside the transaction. Approximate next start for a queued provider is max(previous logical start + configured interval, previous actual completion, provider cooldown, retry eligibility), followed by polling/DB jitter. Recompute after wake-up; do not catch up missed slots with a burst.

Example with configured 10s: a 6s call leaves about 4s of pacing wait; a 14s call leaves no mandatory post-completion wait. Other providers continue on their own clocks. Retry-After and leases can extend eligibility; interval changes must never shorten an existing persisted cooldown/reservation. On restart, respect the stored deadline and any unexpired lease before reserving another start. Configuration changes apply to new reservations; no live hot reload or retroactive rewriting of old deadlines in the initial implementation.

Preserve existing atomic coalescing, force-refresh semantics, cache keys/expiry, attempt identities, quote commits, cancellation fencing and retries. Interval configuration is execution policy, not fare identity: **do not put it in cache keys or invalidate otherwise eligible observations**. Keep concurrency fixed at 1; any overlap experiment requires separate approval. A future second Google transport must share a source-family gate rather than bypass a block; none is added here.

### Phase 3 implementation proposal — smallest changes and safety gates

**Scheduling/configuration change:** add three finite positive seconds fields in config.py and corresponding documented environment variables, read them in default_registry instead of its literal 15. Keep fake behavior and Registration's test-friendly zero interval unchanged. Proposed values for approval:

```text
SKIPLAGGED_MINIMUM_INTERVAL_SECONDS=10
SWOOP_MINIMUM_INTERVAL_SECONDS=5
OCTOTRIP_MINIMUM_INTERVAL_SECONDS=15
```

The variables do not exist yet and have not been added to .env or production Settings. Parse numeric values with clear startup errors; reject NaN/infinity/zero/negative real-provider intervals. Scope: config.py, registry.py, .env.example, README and focused tests. Core claim selection, transactions, schemas and the tick algorithm need no pacing rewrite or migration for this configuration feature.

**Focused correctness work before rollout:**

- Add a short provider-feedback repository operation that atomically raises next_request_at using max(current, feedback_received_at + parsed_retry_after/backoff), independently of result/subscriber fencing. JobRunner must record a genuine rate-limit response even if cancellation/deadline/lease fencing discards that work's results. It must not authorize a retry, renew a lease, write quotes or shorten a later cooldown. Retain normal finish semantics for attempts/results; both paths may safely apply max. Turn the direct-cancellation expected failure into a passing regression.
- Replace OctoTrip's isolated setup sleep with an instance-wide, serialized monotonic HTTP-start gate of ≥1.05s before each initialize/tools-call POST. Wait only the remainder since the previous HTTP start, including across completed searches, and release cancellation-safe locks correctly. Network work stays outside SQLite transactions; this protocol wait belongs inside that provider task, so other providers continue. Keep SQLite rate-limit cooldown authoritative. The queue owner and concurrency-1 restriction remain required; do not claim this local gate coordinates unrelated processes/IP clients.
- Parse Retry-After delta-seconds and HTTP-date at the adapter boundary (UTC reference clock; expired date means zero additional wait; malformed/missing values retain a conservative provider fallback). Preserve sanitized status/code plus delay through nested MCP failures. For swoop, a **minimal pinned SDK patch/upstream release** is required to expose the original Retry-After on SwoopRateLimitError: add a compatible optional retry_after field, populate it at the 429 response boundary, and consume it in _invoke with at least the current 120s fallback. Keep retries=0, decoding, money and request behavior unchanged. Review/approve that dependency patch separately within the implementation change; do not silently monkeypatch private SDK functions in production or upgrade the whole library. If this cannot be delivered, retain the existing swoop schedule and hold the faster-source rollout rather than claiming full Retry-After compliance.
- Record sanitized logical claim/start/end, attempt/operation identity, queue/pacing/protocol wait, error code/HTTP status and offer count for validation. Keep HTTP tool-start evidence distinct from claim times; no source response body, selector, URL or secret in logs. If a future requirement is a strict tool-POST interval as well as logical-operation pacing, put an explicit start gate at that transport boundary; current claim timestamps alone cannot promise it. Do not rewrite leases or add a second provider dispatcher to simulate that guarantee.

**Implementation sequence after approval:** (A) preserve current defaults while landing/reviewing config wiring and deterministic tests; (B) fix the reproduced provider-feedback and transport/Retry-After gaps with synthetic transport tests; (C) approve the exact interval values and any pinned SDK patch, run required checks, then apply the approved values through configuration and controlled worker restart; (D) optional separately authorized low-volume canary, with immediate rollback to 15/15/15 on rejection. Preserve a longer provider cooldown even during rollback. No automatic live CI benchmark, interval ramp, production rewrite, SDK fork or restart has occurred in this review.

### Expected performance using measured service times

For N sequential operations, a simple latency-replay model is T(I) = final latency + sum(max(I, each preceding latency)); actual operation starts also include polling/SQLite overhead, retries and cooldowns. Replayed the **same 12 measured non-15s service times** per source at baseline/proposed intervals, without making more requests:

| Source | Model at 15s | Model at proposal | Model improvement |
|---|---:|---:|---|
| Skiplagged, 12 searches | 169.840s | 114.840s at 10s | 32.4% less elapsed time; dispatch ceiling rises from 4 to 6/min when calls finish before the interval |
| swoop, 12 searches | 165.252s | 55.252s at 5s | 66.6% less elapsed time; dispatch ceiling rises from 4 to 12/min when eligible |
| OctoTrip, 12 searches | 265.917s | 265.917s at retained 15s | No change from the proposal; latency/concurrency remains the bottleneck |

These are service-time replays, not observed production gains or independent latency distributions. They exclude job admission, cache hits, shared subscribers, repricing, lease recovery and future throttling. Different providers already overlap, so whole-job completion depends on its slowest required provider; the faster sources can finish sooner without necessarily reducing makespan while OctoTrip dominates. In the 1s/2s samples, Skiplagged/OctoTrip idle waits were only tens of milliseconds: lowering their interval again cannot remove the response-duration bottleneck. Any concurrency increase requires a separate study and approval.
