### Checkpoints 4–5 — implementation and offline verification
- Configured the owner-requested C3 defaults above through `WORKER_MAX_IN_FLIGHT`, `<PROVIDER>_CONCURRENCY` and `<PROVIDER>_INTERVAL_SECONDS`; bounded swoop executor capacity follows its setting. These settings do not establish a safe sustained provider rate. P4.8 tested Sk/Octo C3 but found no consistent speed gain; **swoop C3 has no live validation**.
- Reused the existing worker/SQLite/cache path. Atomic admission counts direct work plus shared operations once, with a global ceiling; round-robin providers admit only eligible work. Persistent job dispatch sequences unify direct/shared/reprice fairness, survive restart, and prevent continuous new arrivals jumping ahead forever. Active work IDs/cache keys stay excluded until actual I/O ends, including after lease expiry.
- Start-to-start pacing uses actual adapter entry with a persisted restart deadline; there is no mandatory post-completion sleep. Shared OctoTrip HTTP pacing covers initialize/tool calls across sessions and blocks unsent peers after 429. Logical timeouts retain bounded physical capacity; shutdown drains threads before ownership release. Permanently stuck threads need process termination; upstream exactly-once execution is not promised.
- Fixed late provider feedback independently of result fencing, including cancelled direct work and shutdown-drained threads. Nested MCP HTTP errors/timeouts and Retry-After seconds/HTTP-date are normalized without retaining exception text; swoop retains its conservative 120s fallback because the SDK omits headers. Retry budgets, cache keys, pricing, normalization, UI and historical-result handling are unchanged.
- Tests: `pytest -c backend/pyproject.toml backend/tests scripts/benchmarks/test_p48_scheduler_review.py scripts/benchmarks/test_p48_failures.py scripts/benchmarks/test_p48_instrumentation.py scripts/benchmarks/test_p49_review.py -q` gave **200 passed**, including additive-migration preservation. Coverage includes actual C3 overlap, global/provider ceilings, dispatch gaps, cooldown races, cancellation, late responses, stalled threads, fair direct/shared/reprice dispatch, restart pacing/fencing, concurrent claims, cache coalescing, process crash recovery and DB failures. The final backend contains 158 tests; the isolated suites contain 42.

## Swoop false-empty diagnosis — 2026-11-11

Latest swoop-only job queried HND→CGK for November 11–30, 2026: twenty live
responses marked succeeded_empty/provider_complete=True, zero stored offers and
zero unpriced candidates. This is independent of ranking or cross-source checks.
Two sequential diagnostics for HND→CGK November 20 using the installed SDK and
identical adapter parameters returned HTTP 200, a 94-character response, and a
null RPC flight payload. The second diagnostic extracted only numeric status:
the wrb.fr error block contained status 13 (INTERNAL), with block width one.
No raw responses/selectors were retained. No throttling/blocking was observed.

SDK 0.7 decoder.detect_error_envelope requires an additional typed ErrorResponse
field to recognize the nonzero status; this short error block is missed.
rpc._parse_rpc_response returns None; _selection.search_trip_options converts
None into SearchResult(results=[], is_complete=True). CheapWings consequently
marks a failed upstream response as successful empty and may cache it. This
proves a false-empty path in the reproduced request; historical twenty response
bodies were not retained, so their exact envelopes cannot be proven. Google's
underlying reason for INTERNAL is not supplied by the observed error block.
Next correction: reject nonzero RPC statuses/missing payload before SDK empty
conversion, preserve true valid empties, and invalidate affected cache entries.
