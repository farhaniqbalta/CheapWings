## Findings

- **FACT: Fli works natively on iPadOS with platform TLS.** No Chrome impersonation, no
  WKWebView. This clears the P5.05 must-have gate (Fli is the highest-priority provider).
- **FACT: the same holds for macOS `URLSession`.** OBS: the earlier `/sorry` result came from
  an HTTPX client (`swoop-transport.md:33-35`), so the block looks client-specific rather
  than "anything that is not Chrome". HYP: Python could also drop `curl_cffi`; untested.
- **Risk: page size is ~3.3 MB against the 4 MB body cap** used by both Python and the
  probe. A Google page change could trip `partial_payload`. Real port: raise the cap with
  a streaming search for `ds:1`, or measure headroom per run.
- **Unpriced rows outnumber priced ones (24 vs 22)** for this query, consistent with
  Python skipping empty price heads; not investigated further.
- **S2 build facts:** `wreq 6.0.0-rc.31` + `wreq-util 3.0.0-rc.14` (Chrome149) + UniFFI
  0.32.2 compile for iOS device and simulator. The `prefix-symbols` feature is broken in
  rc.31 (symbols renamed to `build_script_main_*`, link fails) and was dropped. BoringSSL
  needs `IPHONEOS_DEPLOYMENT_TARGET`/`MACOSX_DEPLOYMENT_TARGET` pinned or its objects target
  the newest OS. Whole Release app incl. Rust + BoringSSL: **7.3 MB**.
- **S2 simulator check not possible:** the installed iOS 27.1 simulator runtime supports only
  one device type ("iPhone Duo"); the on-device check replaced it.
- **S4 parity findings:** Rust initially printed `0.00` where Python prints `-0.00` for a
  negative product rounding to zero (fixed). Beyond Python's default 28-digit decimal
  context, Python `as_minor_units` silently rounds and `FXSnapshot.convert` raises while
  Rust stays exact — a latent Python precision limit, unrealistic for fares, kept as a
  documented divergence. The suite never calls `as_minor_units` (coverage gap; parity grid
  covers it).
- **Test-count note:** `pytest backend/tests` (documented command) = 245 tests; the 287 in
  P4.12/P4.13 includes `scripts/benchmarks` tests that README runs with their own config.

## S5 — Rust core vs Swift core on iPad (follow-up, same day)

Owner rescoped S5 to the native iPad app only, with no server: Linux/Colima parity dropped,
no live provider requests. Both cores implement the same slice — money (FX half-even,
minor units, negative zero), itinerary fingerprint (SHA-256 over Python `isoformat()` text)
and ranking (`best_checked_deal`, `lowest_advertised`, Python stable-sort order) — and are
checked against `spikes/core-s5/fixtures.json`, generated from the real Python code
(`gen_fixtures.py`: 3,006 money incl. 989 error cases, 500 fingerprints incl. microseconds
and negative/quarter-hour offsets, 300 ranking lists with deliberate price ties).

| Measure | Rust core (B: rust_decimal, sha2, UniFFI) | Swift core (C: Decimal, CryptoKit) |
|---|---|---|
| Fixtures on iPad (owner-run, Release) | **3,806 / 0 failures** | **3,806 / 0 failures** |
| Fixtures on macOS | 3,806 / 0 | 3,806 / 0 |
| 20 rounds of all cases, iPad | 0.043 s (2.2 ms/round) | 0.531 s (26.6 ms/round) |
| 20 rounds, macOS | 0.064 s | 0.584 s |
| Executable added to a minimal iOS app | +715 KB (74 → 789 KB) | +156 KB (74 → 230 KB) |
| Code | 200-line core + ~70 lines build/packaging | 161-line core + 13-line package |
| First-run correctness | passed first run | passed first run |

Friction observed:
- **Rust:** three cross-compiles per change (~1 min each), generated bindings, XCFramework
  packaging; two Rust XCFrameworks in one app clashed on `include/module.modulemap` (fixed
  with per-module header folders); deployment targets must be pinned. A real app should
  ship one Rust static library, not several, to avoid duplicated Rust runtime code.
- **Swift:** Foundation `Decimal` drops trailing zeros and has no negative zero (custom
  fixed-scale formatter needed); `sort` is not stable (explicit index tie-break needed).
  Two local packages in folders named `swift` collided in Xcode (renamed).

Interpretation:
- **FACT:** both languages reproduce the Python engine exactly for this slice on the iPad.
- **FACT:** Rust is ~12× faster on the iPad for this workload.
- **HYP (strongly supported):** the speed gap is not user-visible. A maximal search is
  ≤120 route/date combinations × ~22 fares ≈ 2,600 offers, about one fixture round
  (~27 ms in Swift), while each Fli page took 0.68–1.02 s in S1 and providers are paced
  1–5 s apart. Swift's cost is mostly `Decimal` and `String(format:)`; it can be optimised
  if a profile ever shows it matters.

## Decision status

- S1 passed → Fli is native on iPad via URLSession in both options; wreq is not needed.
- S4 passed → a Rust core can enter the Python web backend gradually, if ever wanted.
- S5 passed for both → for the owner's scope (**native iPad, no server**), recommendation is
  **C: plain Swift core** — equal correctness, smaller app delta, no bridge or cross-compile
  pipeline, one language with the SwiftUI app; Rust's speed advantage does not change
  time-to-results.
- **When B would win instead:** if the owner later wants the iPad and web apps to share one
  engine binary, the Rust core is the only option proven inside both (S4 + S5). That goal is
  out of the current S5 scope.
- Not decided here (owner): approve C for the P5 iPad engine; whether one-engine-for-web
  remains a goal.
