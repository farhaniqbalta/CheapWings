# P5.3 iPad Persistence and Resume Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A search on the iPad survives leaving the app: progress and results are saved on the device after every route/date, an interrupted search (backgrounded, killed or force-quit) can be resumed from where it stopped, and on iOS 26+ a search the user starts keeps running in the background with system-visible progress.

**Architecture:** A new Rust crate `cheapwings-store` (SQLite via `rusqlite`, system `libsqlite3`) owns the on-device schema and is exposed through the existing single iOS library (`cheapwings-ffi`) as a UniFFI object `SearchStore`. `CheapWingsKit.SearchSession` checkpoints each finished route/date into the store and can resume the pending ones. The app restores the latest search on launch and wraps runs in `BGContinuedProcessingTask` when available.

**Tech Stack:** Rust (`rusqlite`, UniFFI 0.32.2), Swift (CheapWingsKit, SwiftUI, BackgroundTasks), XCTest, XcodeGen.

**Spec:** [P5.05](p5.05.md) §5 (foreground-first, checkpoint/resume default, iOS 26 continued processing as conditional add-on, force-quit not guaranteed), [P5.06 owner decision](p5.06.md#owner-decision-2026-11-13-after-s5) (Rust owns logic incl. optional iPad SQLite; one Rust static library per app), [P5.2](p5.2.md) (engine, session, per-offer filtering).

## Global Constraints

- Still exactly one Rust static library in the app (`cheapwings_ffiFFI`); `cheapwings-store` is linked into `cheapwings-ffi`, not shipped separately.
- `rusqlite` pinned exactly; uses the OS `libsqlite3` (no bundled copy); Swift package links `sqlite3`.
- Database file: `Application Support/CheapWings/searches.sqlite`, file protection `completeUntilFirstUserAuthentication` (writes must work while locked in the background), journal mode WAL.
- Checkpoint granularity: one transaction per finished route/date (its offers, hidden-offer reasons or failure code, plus progress). Never lose a finished route/date; an in-flight one is simply re-run on resume.
- Resume re-runs only route/dates not yet finished, in the original order, with the same 1 s Fli pacing and stop rules; a stop for 429/401/403/block is persisted and resume is offered only as "Try again later".
- Money stays text; offers are stored exactly as the decoder returned them.
- Freshness: every stored offer keeps its fetch time; results older than **60 minutes** are labelled "Older than 1 hour — prices may have changed" (mirrors the backend's 3600 s live-data retention). No automatic deletion of results the user can see; keep the newest **10** searches and prune older ones on each new search.
- Continued processing only on iOS 26+ (`#available(iOS 26, *)`), only on the user's Search/Resume tap, strategy `.fail`, wildcard identifier `dev.cheapwings.app.search.*` in `BGTaskSchedulerPermittedIdentifiers`; progress in route/date units; expiration → stop as `.backgrounded` after checkpoint. If submission fails, the search runs foreground-first exactly as in P5.2. No automatic or scheduled searches.
- Force-quit: no attempt to continue (Apple cancels without callback); next launch offers Resume.
- No live provider requests by the implementer; device check by the owner.

## Review Focus

1. Killing the app between two route/dates must lose nothing already shown: relaunch shows the same offers and "Resume (n of N done)" — Task 1 (store round-trip) + Task 2 (session restore).
2. Resuming must not re-fetch finished route/dates and must not run alongside another search — Task 2.
3. A search stopped by Google (429/403/block) must not offer an immediate one-tap Resume that hammers again — Task 2.
4. A database that fails to open (corrupt file, full disk) must not crash the app: search still works without persistence and says so — Task 1 + Task 3.
5. Changing the form after a stored search must not resume with the new form values (resume uses the stored request) — Task 2.

**Interfaces (Rust, `cheapwings_store`):**
- `pub struct StoredRequest { pub origins: Vec<String>, pub destinations: Vec<String>, pub date_from: String, pub date_through: String, pub currency: String }`
- `pub enum ComboStatus { Pending, Done, Failed }`; `pub struct StoredCombo { pub index: u32, pub route_date: RouteDate, pub status: ComboStatus, pub code: Option<String>, pub finished_at_ms: Option<i64> }`
- `pub struct StoredOffer { pub combo_index: u32, pub offer_index: u32, pub offer: FliOffer, pub fetched_at_ms: i64 }`
- `pub struct StoredSearch { pub id: i64, pub request: StoredRequest, pub created_at_ms: i64, pub updated_at_ms: i64, pub stop_reason: Option<String>, pub combos: Vec<StoredCombo>, pub offers: Vec<StoredOffer>, pub hidden: Vec<(String, u32)> }`
- `pub enum StoreError { Open(String), Sql(String), NotFound(i64) }` with `code()`
- `pub struct Store` — `open(path: &str) -> Result<Store, StoreError>` (creates schema, `PRAGMA user_version = 1`, WAL); `create_search(&self, request: &StoredRequest, combos: &[RouteDate], now_ms: i64) -> Result<i64, _>` (all combos `Pending`, prunes to newest 10); `finish_combo(&self, search_id: i64, index: u32, offers: &[FliOffer], hidden: &[String], failure: Option<&str>, now_ms: i64) -> Result<(), _>` (one transaction; idempotent: re-finishing replaces that combo's offers); `set_stopped(&self, search_id: i64, reason: &str, now_ms: i64)`; `clear_stopped(&self, search_id: i64)`; `latest(&self) -> Result<Option<StoredSearch>, _>`; `pending(&self, search_id: i64) -> Result<Vec<StoredCombo>, _>`.
- Stop reasons stored as text: `finished | cancelled | rate_limited | blocked:<detail> | backgrounded`.

**Interfaces (Swift via UniFFI):** `final class SearchStore` with `init(path:) throws(StoreError)` and the methods above in camelCase (`createSearch`, `finishCombo`, `setStopped`, `clearStopped`, `latest`, `pending`); records `StoredRequest`, `StoredCombo`, `StoredOffer`, `StoredSearch`, `HiddenCount { reason, count }`; enum `ComboStatus`.
