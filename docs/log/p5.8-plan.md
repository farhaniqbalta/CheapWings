# P5.8 iPad Parallel Fli Pacing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make iPad searches about as fast as the web (a 120-search job in ~35 s instead of ~2.5 min) by starting a Fli request every 0.25 s with several in flight, without changing what gets saved, stopped or resumed.

**Architecture:** `SearchEngine` keeps its public API (`run(_:combos:) -> AsyncStream<SearchEvent>`) and its event contract, but fetches with start-to-start pacing: a launcher starts request *k* at least `interval` after request *k−1* started, up to `maxInFlight` requests at once. Replies are released to the stream **in plan order** (a reorder buffer), so `SearchSession` checkpoints, `DaySummary`, Resume and the store are untouched. A request's slot frees only when its result is released in order (natural back-pressure; `maxInFlight: 1` reproduces today's sequential engine exactly). Any stop (429, 401/403, refused redirect, traffic page, offline, cancel) halts launching, cancels in-flight requests and discards results not yet released — they stay pending for Resume.

**Tech Stack:** Swift structured concurrency (`withTaskGroup`, actor), XCTest, CheapWingsKit; app wiring in SwiftUI. No Rust change (the Rust scheduler stays in P5.4).

**Spec:** [p5.5-fli-interval.md](p5.5-fli-interval.md) (owner decision: 0.25 s for web and iPad; "start-to-start pacing with up to ~5 requests in flight on the iPad … deferred to after P5.6"), [p4.12.md → Fli ladder](p4.12.md#conservative-live-fli-ladder-owner-approved) (peak in flight ≈ latency ÷ interval = 5 at 0.25 s; min start gap ≥ interval), [p5.6.md](p5.6.md) (offline pause, in-order checkpoints), [p5.3.md](p5.3.md) (checkpoint per finished route/date, Resume, 30-min cooldown after a Google stop), owner order 2026-11-14 (P5.6 → this → P5.4 → P5.7).

## Global Constraints

- Start-to-start interval 0.25 s (existing default `SearchEngine(interval:)`); actual gap between request starts never below the interval.
- `maxInFlight` default 6 (web measured peak 5 at 0.25 s with ~1 s latency; 6 leaves headroom for one slow reply without letting a stalled network pile up requests). Configurable in `init`.
- Events keep today's contract and order: per route/date its `.offers` / `.offersHidden` / `.comboFailed`, then exactly one `.progress`, in **plan order**; one final `.stopped`. Nothing is delivered after a stop or cancel.
- Stop rules unchanged: 429 → `.rateLimited`; 401/403 → `.blocked("http_4xx")`; refused redirect → `.blocked(host+path)`; `auth_denied` page → `.blocked("auth_denied")`; offline codes (incl. DNS/host) → `.offline`; other transport errors → `.comboFailed("network")` and continue.
- A stop decided on route/date *k* releases nothing for *k* and later, even if their replies already arrived; they remain pending in the store, so Resume refetches them (never a lost day, never a duplicate saved day).
- On stop or cancel: no new requests start; in-flight requests are cancelled; late replies are ignored.
- No live provider requests by the implementer. Owner device check is the first live run at this rate from the iPad.
- Keep Discover seams (docs/02): the engine still takes an explicit route/date list.

## Review Focus

1. Google says 429 on request 3 while 4–7 are already in flight → search stops as rate-limited, offers from 1–2 kept, 3–7 never saved, all in-flight requests cancelled, Resume (after cooldown) fetches 3 onward — Task 1.
2. Replies arrive out of order (request 2 slow, 3–5 fast) → the results list and checkpoints still advance 1, 2, 3 … with no gaps or duplicates — Task 1.
3. Network stalls (every reply hangs) → never more than `maxInFlight` requests open; Cancel ends them all — Task 1.
4. Wi-Fi drops while 5 requests are in flight → one `.offline` stop, no `comboFailed` for the others, all pending for Resume — Task 1.
5. Starting a new search or Resume while an old one is still draining → never two engines' requests interleaving (existing generation guard) — Task 2 (existing test re-run).
