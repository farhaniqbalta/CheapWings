# P7.4 Discover runtime Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run Discover end to end on both platforms with fake providers: Skiplagged "anywhere" observations → `select_discovery_plan` → ordinary detailed checks, durable across restart, cancel and rate limits.

**Architecture:** Two stages, `discovering` then `checking`, inside the existing runtimes (spec §6).
- **Shared core:** Rust parses the anywhere reply. Each platform makes its own calls through its existing Skiplagged transport.
- **The single transaction:** the observation snapshot, the plan and the detailed work items are written together, in one SQLite transaction on the iPad (`cheapwings-store`) and in one `Repository.finalize` write session on web.
- **Nothing new on top:** no new scheduler, worker or job model.
- **Order:** iPad first, then web. There are three PRs (A, B, C below), each gated by the owner.

**Tech Stack:** Rust (`cheapwings-core`, `cheapwings-store`, UniFFI, PyO3), Swift (CheapWingsKit), Python (FastAPI, SQLAlchemy, Alembic).

**Spec:** `docs/log/p7-handover.md` §2.3, §6, §9. Provider mapping: `docs/log/p7.1.md` "Adapter mapping". Contract: `docs/log/p7.3.md`.

## Global Constraints

- PRs target `p7-implementation`. The owner merges. No live provider calls in tests or CI.
- Search behaviour, Search fixtures and Search API responses stay unchanged.
- Core commits run `sh core/update-expected-revision.sh`. CI commands are the same as in `docs/log/p7-plan.md`.
- **Fixed values:**
  - `MAX_DISCOVERY_CALLS = 31`: origins × days per Discover run. This is the owner gate in Task 1.
  - `max_route_dates = 120`, the same route/date cap as Search's `max_combinations`. Detailed work items = route/dates × enabled detailed providers, exactly as in Search, so no new limit exists.
- **FX:** `FxRate{USD, pricing.rate}` from the same anywhere reply, the same source as the detailed Skiplagged parser. The snapshot stores every call's rate. Selection takes one rate per currency (the P7.3 API), so it uses **the rate from the last successful call**. The calls run within a couple of minutes, and the probe's rates shared one `rateAsOf`. This corrects p7.1's "CheapWings' own FX snapshot".
- **Wording:** "source unavailable" (every discovery call failed), "no prices" (calls succeeded, nothing priced) and "none under budget" are distinct outcomes. Never "0 flights" after an upstream failure.
- **Fli Explore is out of scope:** the backend pin bump isn't approved. Adapters stay provider-keyed so it can be added later.

## Review Focus

1. **Restart after the snapshot is committed but before detailed work starts:** the plan is not re-run and work is not enqueued twice. Pinned in Task 3 `commit_discovery_is_once` and Task 9 `finalize_plans_once`.
2. **Every discovery call fails (403, offline or schema change):** the run ends as "source unavailable", not "no destinations". Pinned in Task 5 `all_calls_failed_is_unavailable` and Task 9 `discovery_all_failed_is_unavailable`.
3. **A 429 with a long Retry-After during discovery:** the source stops and is cooled down, with no silent long sleep. Pinned in Task 5 `long_retry_after_stops_source`.
4. **Some calls fail and others succeed:** the plan uses what arrived and the failed calls are counted. Pinned in Task 5 `partial_discovery_plans_from_survivors` and Task 9 `partial_discovery_plans`.
5. **An old v2 iPad database or an existing web DB:** it opens and keeps its Search history. Pinned in Task 3 `v2_file_migrates` and Task 7 `migration_keeps_search_rows`.

### Task 5: Discovery stage in `SearchSession`

**Files:** `SearchSession.swift`, `SearchEngine.swift` (`SearchRequest` gains `kind` and `budget`), a new `DiscoveryStage.swift`, and a test in `CheapWingsKitTests/DiscoverySessionTests.swift`.

**Interfaces — Produces:**
- `SearchSession.startDiscover(_ request: SearchRequest)` (with `kind == .discover`). It reads `public private(set) var discovery: DiscoverySummary?`, where:
  ```swift
  public struct DiscoverySummary: Equatable, Sendable {
      public var callsPlanned, callsDone, callsFailed, unpriced: Int
      public var counts: DiscoveryCounts?      // after selection
      public var leads: [DiscoveryObservation] // the snapshot, for the UI's provisional leads
  }
  ```
- `EmptyOutcome` gains `.sourceUnavailable` (every call failed or stopped) and `.noPrices` (calls succeeded, no observation selected).
- **`DiscoveryStage.run(provider:calls:currency:sleep:) async -> (observations, fx, failed: Int, stop: StopReason?)`:**
  - Calls run sequentially at `provider.pacing.interval`.
  - A `.retry` waits and retries up to `PacedRunner.maxAttempts`. A wait over `PacedRunner.maxRetryWait` stops the source as `.rateLimited`.
  - A `.stop` ends the stage.
  - Cancel and `pauseAfterCurrentRequest` are honoured between calls.
  - `shortcut: one call in flight (≤31 calls × 3 s), raise to the provider's maxInFlight if discovery feels slow`.
- **Then, on the main actor:**
  1. Run `selectDiscoveryPlan(observations, query, fx, 120)`.
  2. Build `items = request.items(selected route/dates)` for the enabled detailed providers.
  3. Call `store.commitDiscovery(...)`.
  4. Hand over to the existing `launch(...)`.
- **Restore:** a stored search with stage `discovering` restarts discovery from scratch, since nothing was persisted. Stage `checking` resumes like any search.

### Task 9: Runner and finalize: discovering → checking in one transaction

**Files:** `application/job_runner.py`, `storage/repository.py` (`finish`, `finalize`, `claim`), and a test in `backend/tests/integration/test_p74_discover_lifecycle.py`.

**Interfaces:**
- **`JobRunner.invoke`:**
  - `work_type == "discover"` calls `provider.discover(DiscoveryRequest(...))`.
  - `execute` builds that request from the item.
  - `validate_result` checks `provider_id` and `request`.
- **`Repository.finish`** for a discover item writes its observations and FX rows in the same session that marks the item finished. The lease token fences it, so a late duplicate can't write twice.
- **`Repository.finalize`:** when `job.kind == "discover"` and `job.phase == "discovering"` and no discover item is active:
  1. If no discover item succeeded, then `status="failed"`, `phase="done"`, and the projection reports `discovery.outcome="unavailable"`.
  2. Otherwise, in the same session:
     - Load the observations, plus the FX row from the last successful discover item.
     - Call `cheapwings_core.select_discovery_plan` with `max_route_dates = settings.max_combinations` (120).
     - Insert detailed `WorkItem`s, selected route/dates × detailed registrations, through the same code path `create_job` uses, including `prepare_cached_work`.
     - Set `phase="searching"`.
     - Store `counts` in `job.discovery_json` (from Task 7).
  3. If nothing was selected, the job ends `completed`, with outcome `no_prices` or `none_under_budget` depending on `counts.over_budget`.
- The guard on `phase == "discovering"` makes the step idempotent.
