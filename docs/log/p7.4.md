# P7.4: Discover runtime

Plan: [p7.4-plan](p7.4-plan.md). Three PRs into `p7-implementation`: A (shared core), B (iPad), C (web).

## PR A: shared core (Tasks 1–2)
- **`discovery_sources::discovery_calls(query)`:** origins in query order, then each day. It uses the same validation as `select_discovery_plan`. More than `MAX_DISCOVERY_CALLS = 31` (owner-approved 2026-11-22) gives `too_many`.
- **`discovery_sources::skiplagged_anywhere(rpc_json, origin, depart, fetched_at)`:** a raw `sk_destinations_anywhere` reply becomes `AnywherePage{observations, fx, unpriced}`, using the p7.1 mapping:
  - The amount is the exact USD lexeme.
  - `Standard` maps to `no`, anything else to `unknown`.
  - Only skiplagged.com deep links are kept, with `utm_*` stripped.
  - Rows without a USD price are counted as `unpriced`.
  - FX = `[{USD, pricing.rate}]` from the same reply.
- **Bindings:**
  - Swift: `discoveryCalls(query:)` and `skiplaggedAnywhere(rpcJson:origin:depart:fetchedAt:)`.
  - Python: `cheapwings_core.discovery_calls(json)` and `cheapwings_core.skiplagged_anywhere(json)`.
- **Fixture:** `contracts/fixtures/core/discovery_sources_fixtures.json`, generated by `scripts/gen_discovery_sources_fixtures.py`. It has the 6 recorded P7.1 probe replies, 4 hand-written replies and 5 call-plan cases.
- CI now also runs on PRs into `p7-implementation`.

## PR B: iPad runtime (Tasks 3–5)
- **Store v3 (`cheapwings-store`):**
  - `StoredRequest` gains `kind` and `budget` (JSON with serde defaults, so old rows load).
  - New `searches.stage` and `searches.discovery_meta` columns, plus an `observations` table.
  - `create_discovery` starts a search in `discovering` with no work items.
  - `commit_discovery` saves the snapshot, FX and call counts, inserts the work items and moves the search to `checking`, all in one transaction. It is refused (`already_committed`) unless the stage is `discovering`.
  - A real v1 file and a real v2 file both migrate.
- **`SkiplaggedDiscoveryProvider`:** `sk_destinations_anywhere` over the existing MCP client. The 429/401/403/offline/cancel mapping is now one helper shared with detailed search. Parsing is in Rust.
- **`SearchSession.startDiscover`:**
  - Discovery calls run one at a time at Skiplagged's 3 s pacing.
  - A Retry-After of 2 min or less is retried, up to 3 attempts. A longer wait stops the source as rate-limited, with no long silent sleep.
  - A provider stop keeps the leads that arrived. Offline, cancel and background save nothing, and Resume re-runs discovery.
  - Then `selectDiscoveryPlan`, using the last successful call's rate and the 120 cap, then `commitDiscovery`, then the existing paced checks. A source that stopped us is not used for checks in that run.
- **Restore:** a search still in `discovering` restores as `interrupted` and resumes by re-running discovery. A committed search resumes only its pending checks, and its selection counts are recomputed from the snapshot.
- **Empty outcomes:** `EmptyOutcome` gains `.sourceUnavailable`, `.noPrices` and `.noneUnderBudget`, with minimal labels in `ResultsView`. The real Discover UI is P7.6.

## PR C: web runtime (Tasks 6–10)
- **Adapter:**
  - `ProviderCapabilities.destination_discovery` is added last, defaulting to false, and is also in the capabilities DTO and OpenAPI.
  - `SkiplaggedProvider.discover(DiscoveryRequest)` calls `sk_destinations_anywhere`. `mcp_search` and its exact-number capture are now parameterized by tool and key. Parsing is the shared `cheapwings_core.skiplagged_anywhere`.
  - `FakeProvider.discover` returns synthetic, scriptable leads.
- **Storage:** migration `b7d3e91c2f40` adds `search_jobs.kind` (default `search`) and `search_jobs.discovery_json`, plus a `discovery_observations` table with a unique `(work_item_id, idx)`. It uses plain `ADD COLUMN`, because a batch rebuild trips existing foreign keys.
- **Jobs:**
  - `DiscoverQuery` is validated by the shared `discovery_calls` and carries Search's fixed fields, so cache keys, result storage and reprice read it unchanged.
  - `Repository.create_discovery_job` creates one `work_type="discover"` item (destination `*`) per call per discovery source, with the same capacity checks as Search.
- **Lifecycle:**
  - The runner routes `discover` items to `provider.discover`.
  - `finish` writes a discover item's observations in the same lease-fenced session.
  - `finalize` plans once, guarded by `phase == "discovering"`, when no discover item is active. In that same transaction it runs `select_discovery_plan` (120 cap, last successful call's FX), inserts the detailed checks and sets the phase to `searching`.
  - The outcome is one of `planned`, `no_prices`, `none_under_budget` or `unavailable`. If every call fails, the job is `failed` with outcome `unavailable`.
- **API:**
  - `POST /api/v1/discover` returns 202 with `Location: /api/v1/discover/{id}`.
  - `GET /api/v1/discover/{id}` returns `DiscoverJob`: discovery coverage, check counts, and the honest wording "Lowest fares found among N discovered destinations; M checked."
  - `/discover/{id}/results` reuses the results projection. `/discover/{id}/cancel` cancels.
  - Search endpoints and bodies are unchanged. A Discover id on a Search endpoint gives 404, and the other way round too.

**Limitations:**
- Discover checks run as direct work items and don't use the shared provider cache, because `finalize` has no registry. This is marked as a `shortcut:` in the code.
- A discovery-only source would count as "unavailable" under the existing registry rule. Skiplagged both discovers and checks, so it isn't affected.
- Observation rows are kept with the job and aren't purged with expired fare data.
- There is no web UI yet; that's P7.5.
- Fli Explore is not included: the pin bump needs the owner's decision.
