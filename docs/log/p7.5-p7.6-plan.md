# P7.5 / P7.6 Discover UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** A `Search | Discover` choice on web (P7.5) and iPad (P7.6). Discover shows discovery progress, provisional leads and checked fares, with honest coverage wording.

**Architecture:** UI only, on top of the P7.4 runtimes.
- Web polls `GET /api/v1/discover/{id}` and `/discover/{id}/results`.
- The iPad drives `SearchSession.startDiscover` with `SkiplaggedDiscoveryProvider`.
- Both show a destination list. Each row has the provisional discovery price and, once checked, the cheapest checked fare. Checked fares rank first.
- Small, pure row builders (TypeScript `src/lib/discover.ts`, Swift `DiscoverRows.swift` in CheapWingsKit) carry the logic and are unit-tested. Views stay thin.

**Spec:** `docs/log/p7-handover.md` §2.2, §2.3, §7. Runtime: `docs/log/p7.4.md`.

## Global Constraints
- Search behaviour, forms and results stay unchanged. Discover is a separate mode.
- **Wording:**
  - The coverage line is "Lowest fares found among N discovered destinations; M checked". Never "cheapest anywhere".
  - Provisional discovery prices are labelled "Discovery price (provisional)" and are visually separate from checked fares.
  - Each outcome gets its own message: unavailable, no prices, none under budget, timed out.
- **Limits:** at most 31 discovery calls (origins × days), shown before submit.
- **Process:** no live provider calls in tests. PRs target `p7-implementation`, stacked on #29 until it merges.
- Existing visual conventions apply: P4.6 web styles and the SwiftUI `Theme`.

## Review Focus
1. **Every discovery call failed:** the screen says the source was unavailable, not "no destinations". Pinned in web `outcomeMessage` and the browser test, and in iPad `DiscoverRowsTests`.
2. **A destination with a lead but no checked fare yet:** it shows the provisional price as provisional, never as a checked fare. Pinned in `discoverRows` tests on both platforms.
3. **A checked fare cheaper or dearer than its lead:** checked fares rank first, by checked price. Pinned in the `discoverRows` tests.
4. **More than 31 calls:** submit is disabled and the reason is shown before any request. Pinned in `discoveryCallCount` and the browser test.
5. **Restoring a Discover job from the URL, or relaunching on the iPad:** the Discover view comes back, not the Search view. Pinned in the browser test and in iPad session restore (existing P7.4 tests, plus a model check in the app build).

### Task 2: Web types, client and row logic
**Files:** `apps/web/src/api/types.ts` (`DiscoverRequest`, `DiscoverCreated`, `DiscoveryStatus`, `DiscoveryLead`, `DiscoverJob`), `src/api/client.ts` (`createDiscovery`, `getDiscovery`, `getDiscoveryResults`, `cancelDiscovery`), `src/lib/discover.ts`, tests in `apps/web/tests/discover.test.ts`.
**Produces:**
- `discoveryCallCount(origins: string[], from: string, through: string): number` returns origins × inclusive days, or 0 for an invalid or reversed range. `MAX_DISCOVERY_CALLS = 31`.
- `outcomeMessage(outcome, status): string | null`.
- `discoverRows(job: DiscoverJob, itineraries: Itinerary[]): DiscoverRow[]` returns one row per shortlisted destination: `{destination, date, origin, leadAmount, checkedAmount | null, checkedItineraryId | null, state: "checked" | "checking" | "no_fare"}`. Rows with a checked fare come first, by checked amount, then the rest by lead amount.
- [ ] **Tests** cover: the call count (7 for one origin over a week, 0 when reversed), all five outcomes, a lead with no fare (provisional), and checked-before-lead ordering. Run `npm test`: FAIL, then implement, then PASS.
