### Viajante vs swoop — source-level findings and benchmark gate

- Transport difference is real in inspected code: Viajante defaults to public Google Flights bootstrap data; current swoop uses RPC. Both depend on Google. Viajante's standard sweep can send eight concurrent GETs (conservative mode two); neither mode establishes a 15-second request interval. An adapter must dispatch single route/date units under our existing pacing, constrain SDK retries, and share Google-family cooldown if both transports are ever enabled. Switching transports after a source block is not an acceptable retry strategy.
- **Money blocker:** [models_flights.py](https://github.com/felipebasurto/viajante/blob/377adfd3d9504d62bf26543eaf62c62bdd2356a5/src/viajante/models_flights.py) declares `FlightOffer.price: float`; [parsers.py](https://github.com/felipebasurto/viajante/blob/377adfd3d9504d62bf26543eaf62c62bdd2356a5/src/viajante/parsers.py) parses monetary text using float. [google_flights_rpc.py](https://github.com/felipebasurto/viajante/blob/377adfd3d9504d62bf26543eaf62c62bdd2356a5/src/viajante/google_flights_rpc.py) also accepts numeric prices and formats price_text from them. Converting the high-level float to Decimal afterward does not restore original precision, and price_text is not always untouched source text. No high-level drop-in integration under our money invariant. A separately maintained Decimal-preserving decoder/transport boundary or upstream change must be proven first, including fractional USD/AUD, IDR/JPY and locale separators.
- **Recheck semantics:** [recheck.py](https://github.com/felipebasurto/viajante/blob/377adfd3d9504d62bf26543eaf62c62bdd2356a5/src/viajante/recheck.py) issues a fresh search, compares flight numbers/clocks/routes, and optionally permits weaker carrier/time matching. It does not establish same seller/fare/baggage/mandatory fees. Its same_price outcome must never map directly to CheapWings repriced_exact. Disable loose matching for any identity comparison; use our own complete segments/fare evidence requirements. Missing operators/timezones must stay unknown.
- Promising additions: explicit partial/empty/error envelope, per-field evidence, Google public-page transport and one-way flexible-date primitives. ### Current code audit — implications for caching

- `Repository.create_job` in `storage/repository.py` always creates new work items. Current persistence is result retention/job recovery, not cross-search observation reuse. Sorting/pagination already query stored results and make no upstream calls.
- `SingleDateRouteQuery` contains origin/destination/date, basic/hidden-city flags, display currency and optional POS. Adults=1/economy are enforced in SearchQuery and adapters; max_stops and checked_bags_required are job-side comparison controls, not forwarded provider query fields. Do not add fictitious supported filters to a key/interface.
- Swoop resolves an omitted POS using the display currency; Skiplagged rejects explicit POS/basic-exclusion and currently sends includeHiddenCity=False even for an opt-in query. Keys must isolate requested semantics and record effective source settings; cache cannot silently broaden capabilities or repair provider filtering.
- `Registration.can_cache=True` is a local policy flag, not independent evidence of upstream reuse rights. Existing personal-use acceptance stays intact. Add explicit per-provider reuse caps/policy version for any approved cache; unknown new-provider policy defaults to disabled. Do not derive authorization from a software MIT license or result-validity hint.
- `provider_complete` means source-response scope, **not exhaustive fare inventory**. Swoop requires the SDK boolean; Skiplagged derives completeness only when hasMoreResults is an actual boolean. Redacted P0 evidence has swoop is_complete=true, but one Skiplagged fixture has hasMoreResults=true. Strict complete-only caching will intentionally miss truncated/unknown Skiplagged responses. Swoop may also return unpriced candidates even when its response is complete: initial cache eligibility should require unpriced_candidate_count=0. This limits expected hit rate; no measured cache benefit is claimed.
- `data_expires_at` currently starts at job creation, not quote retrieval; config caps live retention to 60..3600 seconds. Purge removes quote revisions, quote/segment/itinerary data and FX. GET results returns 410 at the deadline, while GET status remains available with an expiry warning. Cache reuse must preserve that behavior and absolute originating cutoffs instead of starting another hour on each hit.
- Existing `_store_results` applies job-specific comparison rules and links quotes to job/work identities. Cache snapshots should be captured before those job-specific transformations, then re-run them for each consumer. Otherwise required-bag/stop settings may inherit another job's eligibility. Preserve airport transfers, carrier names, warnings, original timestamps and FX observations.
- `schedule_verification` waits until no active work remains and `claim` orders by creation/date. Caching alone does not address the previously observed long wait for repricing. Incremental verification and a fair bounded priority rule remain a separate engineering task; avoid quietly combining both scheduler redesigns.

### Proposed cache design — reviewable specification, not implemented

**Recommendation:** a SQLite cache of immutable, normalized per-provider route/date observations, initially feature-flagged off until approved. Proposed defaults: `SEARCH_CACHE_ENABLED=false` for rollout, `SEARCH_CACHE_TTL_SECONDS=1200`, `SEARCH_CACHE_MAX_ENTRIES=2000`, plus a serialized-payload byte budget. The handoff's enabled=true example is a proposal, not authority to activate production caching. Twenty minutes is a reuse limit hypothesis, not measured fare stability. Existing live retention must not increase.

**Policy and eligibility:** allow reuse only when the provider registration explicitly permits the current personal scope and the source response succeeds with provider_complete=true, zero unpriced candidates and valid normalized content. Both SUCCEEDED_RESULTS and proven SUCCEEDED_EMPTY may qualify. Failures, partial/unknown/truncated responses and reprice failures are misses; do not negative-cache them as no flights. Distinguish complete source response from exhaustive inventory forever. New sources remain cache-disabled until reviewed. Existing accepted sources retain the same personal risk decision; this design creates no new claim of written upstream rights.

**Canonical key v1:** SHA-256 of a deterministic, schema-versioned JSON object; compare stored canonical key as well as hash. Include provider_id; pinned SDK, parser/adapter and canonical-payload versions; airport/timezone reference version when normalization depends on it; single explicit airport pair and origin-local departure date; trip_type=one_way, adults=1 and cabin=economy; requested include_basic_economy/include_hidden_city; requested and effective currency/POS; actual source query defaults (e.g. limit, locale and exclusion flags); requested max_stops/checked_bags_required as conservative job-filter isolation; configured use scope/policy version. No user token, signed URL, quote selector or arbitrary endpoint in keys/logs. Normalize unordered selections but never route/date identity.

The current provider query lacks adults/cabin/stops/bag fields: validate the fixed adult/cabin constraints from the job, record the fixed values, and bind job-filter fields at the cache boundary without pretending they were sent upstream. A filtered payload must never masquerade as an unfiltered source response. Persist the sorted selected-provider set on the job; conservatively include its digest in v1 keys to honor the supplied handoff's no-reuse-across-different-selections rule. This reduces reuse when sources change; a future explicit contract decision could permit individual selected-provider entries to be reused across sets while keeping all required provider work, but must not silently relax this rule. Overlapping route/date windows with the same selections still reuse entries.

**Three distinct clocks:**

- `observed_at`/retrieved_at and upstream source_checked_at: immutable source evidence; do not overwrite with cache access time or invent a source observation time. If upstream already cached the observation, preserve the older known source time; unknown age is disclosed and cannot satisfy a strict freshness promise.
- `fresh_until`: min(original freshness basis + configured TTL, provider reuse/validity cap, hard retention cutoff). Use an explicit age basis; missing/ambiguous upstream age may require a miss. OctoTrip's advertised 15-minute validity caps a possible reuse TTL below the proposed global 20 minutes; it does not by itself approve caching. Never extend freshness on a hit or duplicate write. At now >= fresh_until, lookup must miss even before cleanup.
- `hard_expires_at`: original absolute permitted retention cutoff; cache copies, follower jobs, revisions, selectors and FX evidence cannot extend it. Delete cache payload by freshness expiry; independently delete copied result payload by hard expiry. No stale-while-revalidate behavior in the first version. Existing jobs may still show age-labeled observations within their retention period after reuse freshness ends; that is not permission to reuse them for a new search.

**Proposed tables and ownership:**

| Storage addition | Purpose and minimum fields |
|---|---|
| provider_result_cache | Immutable snapshot id, key digest + canonical key/version, provider/policy versions, observed_at/retrieved_at, cached_at, fresh_until, hard_expires_at, terminal source outcome, complete flag/counts, canonical payload JSON/text with decimal strings, byte size. Index key/fresh_until and expiry. No public raw payload. |
| provider_operations | Job-independent upstream operation: id/key, state, creation/deadline, retry time, lease token/until, attempts, policy/retention cutoff, produced snapshot ref. Unique active operation per normal key, enforced in SQLite transaction/index. Preserve provider-wide pacing and attempt evidence. |
| WorkItem additions | Operation/snapshot association, result_origin (`live`, `cache`, `shared_inflight`), reused_at and original observation expiry. WorkItem remains the subscriber's durable coverage record. Cache hits have attempts=0 and no fictitious provider WorkAttempt. |
| SearchJob additions | Persist resolved source selection/cache mode separately from flight-domain fields; durable upstream-work quota classification. Keep submitted query immutable and expose resolved selection deliberately. |

Do not cache a mutated SearchJob or current FareQuote projection: a later reprice revision may have a different seller/product or changed/unavailable status. Snapshot the normalized detailed response before job-specific filtering; preserve every canonical segment/summary/airport transfer, separate seller, attribution, warning, source amount/currency, FX snapshot and original timestamp. Re-materialize job-local quote/itinerary IDs through existing matching/eligibility rules. No inherited prior-job verification revisions or repriced_exact badge. Repricing is separately scheduled within that job's budget.

**Selector policy:** cache opaque handles only server-side under the same permission, original expiry and current usability checks. An observation can remain displayable after its selector expires; mark it non-repriceable rather than regenerating/relabeling the selector. A stale handle must not result in a false exact check. No promise that a cached selector will work: validate once on use and classify failure honestly. Protect handles from OpenAPI/examples/browser/logs, and delete them with snapshot/quote retention.

**Retention implementation choice:** current public results expire job-wide. The smallest compatible first design caps any consuming job's data_expires_at and deadline at the minimum inherited hard cutoff of its reused snapshots and its own configured cutoff. Check that cutoff inside the same transaction as cache attachment and before each result commit; never resurrect an expired job. This may expire fresh sibling observations sooner and is deliberately conservative. At expiry, fence/cancel outstanding work and purge result/revision/FX/cache payloads; retain existing sanitized coverage/status warning behavior and results 410. If this early whole-job expiry proves unacceptable, a per-quote expiry/projection design is a separate contract change with pagination/ranking tests, not an implicit TTL extension. No extending old cutoffs when retention configuration changes.

**Atomic cache hit and in-flight coalescing:**

1. Validate auth, request/source allowlist, policy/SDK availability and query support before any lookup. Begin the existing short SQLite write transaction; lookup unexpired eligible snapshot before consuming provider rate slots or incrementing attempts. On hit, attach/materialize records, mark successful coverage and commit together; finalization retains existing unique-combination counting.
2. On miss, atomically join/create an independent provider_operation by key and subscribe the job's WorkItem. The operation has its own fenced attempt/lease lifecycle; current job-owned running-work semantics alone cannot guarantee cancellation isolation. Do not merely point a follower at another job's running WorkItem.
3. Execute the upstream call outside transactions using current bounded executor, provider concurrency, minimum interval, cooldown and retry budgets. A worker restart may reclaim only expired operation leases; stale completions cannot publish snapshots or duplicate quotes. A no-longer-valid policy/version cannot be revived through a cached operation.
4. Publish validated normalized response, eligible cache entry and subscriber completion atomically with fencing. Re-check subscriber cancellation/deadlines/retention before delivery; one cancelled follower cannot cancel another. With no subscribers, drop pending work; for an uninterruptible running call keep its provider slot until it actually returns, then discard unauthorized/expired delivery. Do not use a cancelled leader's lease to start concurrent duplicate calls.
5. Failures remain operation/coverage errors under bounded retries, never successful empty/cache entries. If a coalesced response is partial and ineligible for cache, subscribers can still receive its explicitly partial evidence; a later new search must miss/revalidate rather than claim a complete cached matrix.
6. Force refresh bypasses completed snapshots. It may only join a genuinely fresh operation started no earlier than that request; an older in-flight observation cannot satisfy it. Otherwise schedule fresh work under pacing/budgets. Serialize by provider/family and never discard another job's operation merely to refresh. Distinct refresh requests remain bounded by request/upstream limits.

**Bounds and quotas:** enforce entry count **and bytes** on insertion in short transactions; evict expired first then oldest reusable snapshots, without deleting already materialized job results before their hard cutoff. Bound waiters/request creation too. Preserve normal owner auth on full-cache hits. Separate user-request abuse limit from upstream-work hourly budget: exempt a fully reused request only from upstream-work quota, not from user-request limits; mixed misses reserve needed work, followers do not double-charge a shared operation. Current all-job 2-active/20-hourly checks cannot be silently bypassed. Add durable counters/reservations and explicit capability fields in the rollout, with transaction-safe admission/refund decisions. Snapshot expiry between admission and dispatch must reserve a live miss within budget or expose quota/skipped outcome, never quietly send unbudgeted requests. Repricing calls count against provider pacing and verification budgets even on an otherwise full-cache job.

**Operations:** additive migration only after approval, upgrade/downgrade and restart tests; no Redis/Celery. Cache lookup enforces expiry even if cleanup has not run. Run bounded cleanup on worker ticks/startup and invalidate policy/parser/SDK-version mismatches. Feature disabled means no lookup/coalescing/new writes, while retained payloads are still purged by deadlines. Cache failure is visible; a healthy miss may use live work only if budgets/policy permit. Never hide DB integrity failures as free cache misses.
